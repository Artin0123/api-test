# api-test 擴充計畫：輪詢轉發、黑名單與 D1 儲存

## 1. 這個專案現在是什麼、要做什麼

現有的 `api-test` 是一個「API 金鑰體檢站」：
在網頁上登記多個 API 服務商（Provider）和一批金鑰，GitHub Actions 每天跑一輪測試，
把哪些金鑰可用、哪些模型的表現如何，展示在網頁上，並發 Discord 通知。

這次要擴充的方向用一句話說：**把「體檢報告」升級成「體檢＋值日」**——
同一批金鑰能直接對外提供轉發服務，並在網頁上多兩個頁面管理它們：

```
呼叫方（軟體） ──請求──> api-test（轉發站） ──往外轉發──> OpenAI / Gemini 等
（例如聊天軟體）          ├─ 依呼叫方指定的服務商轉發
                          └─ 金鑰輪用、避開壞鑰、記錄，都在這裡
```

```
軟體送出  POST https://我的網址/proxy/服務商別名/v1/chat/completions
轉發成    POST https://api.openai.com/v1/chat/completions
```

網址以外的部分（請求內容格式、回覆格式）一律不修改、不重新打包。

三個角色（沿用既有架構的位置）：

- **呼叫方（客戶端）**：任何能自己填 API 網址的軟體，例如聊天軟體、命令列工具。只負責發出請求。
- **本專案（Cloudflare Pages）**：既有的網頁、API 和測試排程都在這裡；這次在其上加「轉發」這個新職責。
- **上游服務**：OpenAI、Gemini 等真正的 AI 服務。

## 2. 既有的、這次不動的

原則：**現有的管理介面與功能一律不改行為**，新東西全部用「新增」的方式疊上去。

| 既有能力 | 現況說明 |
|---|---|
| 來源設定頁（記事本 UI） | Provider 卡片＋金鑰一行一個的文字框，**照舊使用**；金鑰的新增與刪除就靠編輯這個文字框，不做單筆管理介面 |
| 自訂內容 | 每個 Provider 可設定 Extra Body（JSON）與 Custom Headers（同名覆蓋）；**轉發時同樣生效**（見 R1） |
| 定期檢查 | GitHub Actions 每日定時＋手動觸發；`async_test_keys.py` 測試邏輯不改 |
| 測試結果網頁 | 測試結果 Tab：有效／無效金鑰、模型性能、執行進度，照舊 |
| 失效金鑰機制 | 既有黑名單（`dead_keys`）概念與相關端點；轉發的黑名單沿用同一套管理方式（見 R3） |
| 登入門禁 | `ADMIN_PASSWORD`（管理用），登入後 30 天 session cookie |
| 通知 | Discord Webhook（每日測試完成後） |
| 網頁外觀 | 深淺色模式、手機版自適應、Mock 開發模式等既有 UI 慣例，新頁面跟著走 |

## 4. 與 Cloudflare AI Gateway 的關係（本計畫採用混搭）

Cloudflare 有個官方的「AI Gateway」服務，也是做 AI 請求代理，核心功能免費且額度獨立
（不佔 Pages 的請求額度；日誌在免費方案每天 20 萬筆、只保留 3 天，已確認夠用）。
本計畫採用**混搭**：本專案當腦（門禁、輪詢、黑名單、換鑰、UI），
AI Gateway 當轉發的最後一程（上游），白拿它的加值能力。

| 工作 | 誰負責 |
|---|---|
| 門禁（轉發密碼）、輪詢選鑰、失敗計數與黑名單、換鑰重試、自訂 body／header | 本專案 |
| 請求紀錄與分析（成功與失敗、模型、token 用量、成本、狀態碼、耗時，含金鑰標註）、快取、超時保護 | AI Gateway |

接上去的方法：本專案轉發時，上游網址填 AI Gateway 的網址
（它的認證用 Cloudflare API token 只存在本專案的部署設定裡，呼叫方永遠碰不到，
之前「token 太重不適合發給呼叫方」的疑慮就不存在），
並在每筆請求加一個標註（`cf-aig-metadata`）寫明「這次用了哪把金鑰（頭尾幾碼）」，
它的日誌就會記下每把金鑰的使用情況，可在它的儀表板搜尋、篩選。

它能取代的：

- **請求層級的完整紀錄**：成功**與失敗**都有（日誌含狀態碼，儀表板可按錯誤類型與金鑰標註篩選），
  含模型、token、成本、耗時；只留 3 天（已確認夠用）。因此本專案不再自建紀錄頁（見 R7）。
- **快取**：完全相同的請求可直接回，省 token（聊天大多不重複，當作順手福利）。
- **超時保護**：上游太久沒回應就提前切斷（可選）。
- **它沒有、也替代不了的**：失敗計數與禁用的狀態帳本——這是即時的控制資料，
  只能記在本專案的資料庫（key_state 表），與「給人看的紀錄」是兩回事。

它不能取代的（本計畫照做）：

- 自動輪詢（它預設永遠用同一把金鑰，不會輪）。
- 失敗換鑰重試（它的重試都是同一把金鑰，不會跳下一把）。
- 黑名單、失敗計數、手動恢復。
- 門禁密碼（給呼叫方的還是單純的轉發密碼）。
- 自訂 body 注入、批量測試、匯出、排序、自訂網頁。

自訂上游：它的「Custom Providers」功能支援任何 HTTPS 的 OpenAI 相容網址
（例如第三方中轉站），在它的儀表板登記一次即可；路徑拼接的細節有已知的奇怪行為，需實測；
登記不了的（如本機 Ollama），該服務商的上游維持直連 `api_base`，不經過 AI Gateway。

不啟用的功能：Guardrails（內容審查，用 AI 掃描對話內容是否有害）與 DLP（掃描個資）
與本專案的金鑰管理無關，而且 Guardrails 會依 token 計費，不開。

## 5. 明確不做的範圍

- 不做多會員註冊、多租戶、計費功能（維持單管理員）。
- 不做權重分配與多機器分發（只做輪流使用）。
- 不改現有的記事本式金鑰 UI：不做單筆新增／刪除／匯入匯出介面（金鑰管理就在來源設定的文字框完成；R8 只加搜尋與刪除確認）。
- 不做冷卻機制：失敗不禁用前照常參與輪用，禁用後一律手動恢復，沒有自動恢復計時。
- 不改寫 `async_test_keys.py` 的測試邏輯（每日測試行為維持原樣）。
- 轉發與管理功能不開放「其他網站的網頁」直接呼叫（呼叫方是軟體或程式；自家管理網頁同域，沒有跨域問題）。
- 不修改非 JSON 的轉發內容（需要補欄位的請求限 JSON 格式；純轉發的內容不受限）。
- 不使用 Redis 或任何常駐伺服器；KV 模式下不提供轉發（原因見 R0、R1；紀錄本就交給 AI Gateway）。

## 6. 功能需求

每條都附「怎麼算通過」的驗收方式。

### R0　儲存層切換（KV ⇄ D1）

- 新增部署設定變數 `STORAGE_BACKEND`，可填 `d1` 或 `kv`；**沒填時預設 `d1`**。
- 既有的全部功能（設定、測試結果、進度存檔、失效金鑰、登入）在兩種模式下都能正常運作：
  - `kv` 模式：維持現狀（每天只跑一次測試，寫入量低，現有功能正常）。
  - `d1` 模式：D1 新增資料庫連結（綁定名稱 `DB`）；現有的每一種資料在 D1 裡有對應的存放方式（見第 7 節）。
- 提供一次性的搬移指令：把 KV 裡現有的資料原樣複製到 D1 的 store 表，
  並從 `app_settings` 的金鑰清單建立 key_state 初始列（全部視為正常、未禁用），搬完即可切換模式。
- 選錯模式時行為明確：例如 `d1` 模式但未綁定資料庫，部署或啟動時回報清楚的錯誤訊息，不靜默失效。

驗收：兩種模式各部署一次，每日測試、網頁查看、登入全部正常；搬移指令把 KV 資料搬到 D1 後切換，資料一致。

### R1　透明轉發

- 轉發功能放在同一個 Pages 專案裡，新網址格式：`/proxy/{服務商別名}/{原本的路徑與查詢字串}`。
  每個 Provider 在編輯面板多一個「轉發別名」欄位（例如 `openai-main`，不可重複），呼叫方的網址填
  `https://我的網址/proxy/openai-main/v1/chat/completions`。
- 只把網址的前段換成該 Provider 的上游網址——預設為該服務商對應的 AI Gateway 網址（見第 4 節；
  AI Gateway 登記不了的服務商退回直連 `api_base`），路徑原樣接在後面；
  其餘全部原樣傳遞，包括串流回覆。
- 轉發請求加 `cf-aig-metadata` 標註（金鑰頭尾幾碼＋服務商別名），
  讓 AI Gateway 的日誌能識別每筆請求用了哪把金鑰。
- 上游回什麼狀態碼，就原樣回給呼叫方（內部另行記錄失敗，見 R3，但不改回覆內容）。
- **沿用來源設定**：該 Provider 的 Extra Body（合併進請求內容）與 Custom Headers（同名覆蓋）
  在轉發時同樣生效；認證標頭由本專案換上當次選中的金鑰
  （OpenAI 類用 `Authorization: Bearer 金鑰`、Gemini 用 `X-goog-api-key: 金鑰`，依 Provider 類型決定）。
- 認證：呼叫方在 `Authorization` 標頭帶**轉發密碼**（部署設定變數 `PROXY_PASSWORD`），
  與管理用的 `ADMIN_PASSWORD` 互相獨立——拿到轉發密碼的人不能進管理網頁。
- 轉發功能需要 D1 模式：`kv` 模式時轉發端點回覆清楚的錯誤訊息，要求切換模式（原因見 R0、第 9 節的額度說明）。

驗收：同一請求分別打官方網址與轉發網址，回覆內容與格式完全相同；串流逐步出字；
設了 Extra Body／Custom Headers 的服務商，轉發時上游實際收到這些內容；
未帶密碼、帶錯密碼、帶管理密碼都會被拒（401）。

### R2　輪流使用

- 同一 Provider 有多把可用金鑰時，優先用「最久沒用過」的那把（效果等同輪流）。
- 被禁用（黑名單）或手動停用的金鑰不參與輪用；失敗但尚未達禁用次數的金鑰**照常參與**（沒有冷卻）。
- 每次成功使用後更新該金鑰的「最近使用時間」。

驗收：連續打 N 次請求（N 等於可用金鑰數量的兩倍），每把金鑰被用的次數相差不超過 1。

### R3　失敗計數與禁用（黑名單）

- 判定標準簡單一致：**上游回非 200 的狀態碼，一律算一次失敗**，不分死因（401、403、429、5xx 都一樣）。
- 每次失敗把該金鑰的「連續失敗次數」加一；達到設定的門檻（預設 3 次，可調）就把金鑰**禁用**（進黑名單），不再參與輪用。
- 成功一次就把連續失敗次數歸零（偶爾失敗一次不會累積成禁用）。
- **恢復一律手動**：在「輪詢轉發」頁對被禁用的金鑰按「恢復」按鈕（可先按「測試」確認可用再恢復）。
  沒有任何自動恢復機制。
- 被禁用的金鑰在來源設定的記事本裡**仍然存在**（文字框不動它），只是狀態被標記為禁用；
  金鑰從記事本被移除時，其計數與禁用狀態一併清除。

驗收：一把金鑰連續失敗 3 次後自動禁用、不再被選用；中間夾一次成功則計數歸零；
按「恢復」後金鑰重新參與輪用。

### R4　換鑰重試

- 遇到失敗時，自動換下一把可用金鑰重發同一個請求。
- 最多換 3 次（連第一次共嘗試 4 把金鑰，次數可調）。
- 重試過程中，請求內容先用文字形式保存，每次重試用它重建請求（聊天請求都是幾 KB 的文字，成本可忽略）。
- 每次失敗的換鑰都依 R3 計數（重試中失敗的金鑰也會被記帳）。
- 搭配 AI Gateway 時，把它自身的重試次數設為 1（只試一次）：
  同一把金鑰的反覆重試沒有價值，失敗就該換下一把，換鑰的節奏才不被拖慢。

驗收：準備一把會失敗的金鑰與一把正常的金鑰，同一請求應自動跳過前者並成功返回；
在 AI Gateway 的日誌中可看到整個過程（失敗嘗試與成功嘗試各一筆，金鑰標註不同，因為每一筆都路經它）。

### R5　即時單鑰測試（含批量測試）

- 在「輪詢轉發」頁的每把金鑰旁放「測試」按鈕：當場對該 Provider 的網址發一筆最小請求，
  回報結果：可用（附回應毫秒數）／不可用（附上游狀態碼）。
- **批量測試**：每張服務商卡片另外提供三個按鈕：
  - 「測試全部金鑰」：該服務商的每一把都測一輪。
  - 「只測有效金鑰」：只測目前狀態正常的那些。
  - 「只測無效金鑰」：只測目前被禁用（黑名單）的那些，用來確認哪幾把已經救得回來。
  - 執行中逐筆顯示進度與結果（可用／不可用＋狀態碼），全部完成後彙整一次。
- 即時測試只驗「金鑰可不可用」，不做多模型矩陣測試（那是每日 GHA 的職責）。
- 批量測試逐把依序進行（不提高併發，避免被上游風控）；被測出的結果即時反映在卡片狀態上，
  詳細的請求紀錄可在 AI Gateway 儀表板查看（即時測試的請求同樣經過它）。

驗收：分別對正常與假金鑰各按一次測試，結果正確；
批量測試的三種按鈕各跑一輪，進度與彙整結果與金鑰實際狀態一致。

### R6　新頁面「輪詢轉發」

- 在現有網頁新增一個 Tab（與「來源設定」「測試結果」並列），登入後可用。
- 每個 Provider 一張卡片，**桌面版一行 3 張、手機版一行 1 張**，卡片包含：
  - 服務商名稱（主域名＋類型）與「已停用」標記（沿用既有慣例）。
  - 轉發網址（含別名）與一鍵複製按鈕；未設別名的顯示提示。
  - 金鑰狀態清單：每把金鑰一行，顯示頭尾幾碼、狀態（正常／禁用）、連續失敗次數、最近使用時間。
  - 每把金鑰的「測試」按鈕（R5）；被禁用的金鑰另有「恢復」按鈕（R3）與「查看 Gateway 紀錄」按鈕（R7）。
  - 卡片層級的批量測試按鈕：測試全部／只測有效／只測無效（R5）。
  - 彙總數字：可用金鑰數／總數。
- 頁面外觀沿用既有的深淺色模式、Modal、手機版自適應等慣例。

驗收：桌面版一列剛好排 3 張卡片，手機版每列 1 張；在卡片上完成一次「測試 → 禁用 → 恢復」的操作。

### R7　查看 Gateway 紀錄（不自建紀錄頁）

- 失敗與成功的請求紀錄都由 AI Gateway 的日誌負責（免費，留 3 天，儀表板可篩選、含金鑰標註），
  本專案**不再自建紀錄資料表與頁面**。
- 本專案的 D1 只存**狀態**（key_state：失敗計數、禁用標記）——這是輪詢與黑名單的即時帳本，
  Gateway 沒有任何 API 能提供，無法省略。
- 「輪詢轉發」頁的卡片上，被禁用的金鑰旁提供「查看 Gateway 紀錄」按鈕：
  帶上該金鑰的標註篩選，直接開到 AI Gateway 儀表板的對應紀錄（近 3 天的失敗詳情、狀態碼、耗時都在那裡）。
- KV 模式下轉發功能本就關閉，本條隨之不適用。

驗收：發生一次「換鑰重試後成功」的請求時，AI Gateway 儀表板能依金鑰標註篩出對應的失敗與成功請求；
被禁用的金鑰可從卡片一鍵開到對應的紀錄。
### R8　來源設定的小增補（不改動既有操作方式）

- **編輯面板加搜尋**：Provider 編輯視窗裡，金鑰文字框上方加一個搜尋框，
  輸入片段後即時高亮符合的行（金鑰多時好找特定那一支）。
- **刪除確認保護（不用彈窗）**：按儲存時，若金鑰數量比原本少，
  儲存按鈕那一排的空間直接**拉高**，就地顯示確認內容，一定看得到：
  - 顯示「即將刪除 X 支金鑰」與「將被刪除」的金鑰清單（顯示頭尾幾碼）。
  - 清單最多直接顯示 5 支，超過的部分用捲軸捲動查看。
  - 按確認後才真正儲存；按取消則回到編輯狀態。
  - 金鑰沒有變少時，該區域不出現，儲存行為與現在完全相同。
- **匯出檔案**：每個 Provider 的金鑰清單可下載成 `.txt` 檔（一行一支，與記事本格式相同，可直接再匯入）。
- **排序按鈕（三段循環）**：金鑰文字框旁的排序按鈕，每按一次切換一個狀態：
  1. **預設**：不排序，保持輸入的原順序。
  2. **小到大**：按 ASCII 小到大排（A-Z，符號與數字也一起排）。
  3. **大到小**：按 ASCII 大到小排（Z-A，符號與數字也一起排）。
  再按一次回到「預設」。純前端排序，改的是文字框本身；**儲存時不做任何自動排序**，存的就是框裡的順序。
- 除此之外，來源設定頁的一切照舊。

驗收：搜尋片段能高亮正確的行；把金鑰從 5 支改成 3 支後按儲存，儲存列拉高顯示「即將刪除 2 支金鑰」與清單，
取消則不儲存、確認後才生效；匯出的 txt 用記事本格式再貼回來可完整還原；
排序按鈕按三次依序呈現「原順序 → ASCII 小到大 → ASCII 大到小」，儲存後的順序與文字框一致。

## 7. 資料表設計（D1 模式）

兩張表。金鑰本體不進資料庫——它們住在原本的 Provider 設定（`store` 表的 `app_settings`）裡；
資料庫只記「狀態」（請求的內容與成敗紀錄由 AI Gateway 的日誌負責，見第 4 節）。

### store（既有資料的對應儲存）

既有 KV 裡的每一種資料（`app_settings`、`results:{指紋}`、`checkpoint:{指紋}` 等）
在 D1 用同一張表對應存放，名稱照舊，切換模式時程式邏輯幾乎不用改：

| 欄位 | 意思 |
|---|---|
| k | 原 KV 的鍵名（如 `app_settings`） |
| v | 原本的 JSON 內容，第一次搬移時直接複製過來 |

> 為什麼這張表沿用 JSON：這些資料永遠整份讀、整份寫（GHA 整包上傳、前端整份渲染、
> 儲存時全量替換），從不需要查其中某一列或改其中一個欄位——SQL 拆表的優勢在這裡用不上，
> 沿用 JSON 反而讓 KV／D1 兩種模式共用同一套讀寫程式碼。
> 需要 SQL 能力的是「每筆請求都要單列更新與條件挑選」的金鑰狀態，那是下一張表 key_state 的職責。
>
> 「指紋（fingerprint）」是專案裡已有的概念：由 `provider_type`＋`api_base` 算出，
> 用來在內部識別同一個服務商節點，改金鑰或模型不會讓指紋變動。

### key_state（金鑰狀態：輪用與黑名單，本計畫新增）

| 欄位 | 意思 |
|---|---|
| id | 編號 |
| fp | 所屬服務商的指紋 |
| api_key | 金鑰字串（與來源設定裡的那支對應） |
| last_used_at | 最近一次被使用的時間（輪詢用） |
| fail_count | 連續失敗次數（成功即歸零；達門檻即禁用） |
| disabled | 是否禁用（0／1） |
| updated_at | 最後更新時間 |

- 金鑰從來源設定移除時，對應的這一列一併刪除。
- 選鑰時的「最久沒用優先」用一條 SQL 完成：挑出 `disabled = 0` 的列中 `last_used_at` 最舊的那把。

## 8. 一筆轉發請求的處理流程

1. 檢查轉發密碼，不對就回 401，結束。
2. 由網址中的別名找出對應 Provider；找不到就回 404，結束。
3. 從該 Provider 的金鑰挑一把：未禁用、最久沒用過的那把（禁用名單與失敗計數在 key_state 表）。
4. 挑不到任何可用金鑰，回覆 503「暫無可用金鑰」，結束。
5. 套用該 Provider 既有的 Extra Body／Custom Headers 規則，並換上選中金鑰的認證標頭。
6. 轉發給上游。
7. 成功（上游回 200）：更新該金鑰的最近使用時間、失敗計數歸零、回傳結果，結束。
8. 失敗（上游回非 200）：記一次失敗（計數加一，達門檻則禁用），
   回到第 3 步換下一把；已重試 3 次就結束。
9. 重試次數用完仍失敗：把最後一次的上游回覆原樣傳回，結束。

## 9. 額度檢查（免費方案夠不夠用）

以「一天 1,000 次轉發」估算（這是實際用量的上限估計，平時約 100～1,000 次；
這只是**假設的用量**，不是上限）：

> 補充：只有觸發程式的請求（`/api/*`、`/proxy/*`）算額度；
> 打開管理網頁、載入頁面樣式腳本等靜態請求，官方明定免費且不限次數。

| 項目 | 每日用量（假設） | 免費上限 | 餘裕 |
|---|---|---|---|
| 動態請求（Pages Functions，與 Workers 共用額度） | 1,000 轉發＋每日測試的少量 API 呼叫＋管理網頁的存取 | 100,000／天 | 約 100 倍 |
| D1 讀取 | 約 2,000 列（每次轉發約 2 列：選鑰＋狀態更新） | 5,000,000 | 約 2,500 倍 |
| D1 寫入 | 約 2,000 列（每次轉發的狀態更新 1–2 列）＋每日測試的存檔幾列 | 100,000 | 約 50 倍 |
| AI Gateway 日誌 | 每筆轉發 1 筆（含金鑰標註） | 200,000 筆／天，保留 3 天 | 約 200 倍 |
| KV（僅 kv 模式） | 維持現狀：每天一次測試的寫入，遠低於上限 | 1,000 筆寫入／天 | 充裕 |
| GHA | 維持現狀：每日一輪 | 既有額度 | 不變 |

補充：kv 模式不能開轉發的原因不是紀錄量（紀錄已交給 AI Gateway），而是
轉發需要每筆請求即時、精準地更新金鑰狀態（輪詢順序、失敗計數）——
KV 是最終一致且寫入上限每天僅 1,000 筆，做不了這種帳本；這正是 D1 的職責。

結論：以每天 100～1,000 次的實際用量，所有額度都有百倍以上的餘裕，完全不用擔心；
成功與失敗的請求紀錄都交給 AI Gateway，本專案的資料庫只處理狀態（key_state），壓力更小。
就算哪天動態請求打滿 100,000，超過部分當天被拒、隔天重置，不會產生費用；真要擴充，Workers 付費方案每月 5 美元給 1,000 萬次。
